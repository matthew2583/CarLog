# Отчёт -  CarLog

## Доменная область

CarLog - приложение для учёта расходов на автомобиль. Пользователь заводит свои машины и ведёт по ним журнал: ТО, ремонты, заправки и т.д. Можно добавить, посмотреть, отредактировать или удалить записи.

## Стек

- **Бэкенд:** Python, FastAPI, Uvicorn
- **Фронтенд:** HTML + CSS + JS
- **БД:** PostgreSQL
- **Миграции:** Alembic
- **Драйвер БД:** psycopg 
- **Валидация:** Pydantic
- **Контейнеризация:** Docker, Docker Compose
- **Зависимости:** Poetry

## Основные сущности

**Car** - автомобиль (id, brand, model, year, mileage)

**Record** - запись обслуживания (id, car_id -> FK на cars, date, kind, cost, note)

Связь один-ко-многим: один автомобиль - много записей. По обеим сущностям реализован полный CRUD через REST API.

## Соответствие 12 факторам

### 1. Кодовая база

Весь код приложения (бэкенд, фронтенд, миграции, Docker-конфиги) находится в одном Git-репозитории.

### 2. Зависимости

Зависимости перечислены в `pyproject.toml` с диапазонами версий, а конкретные версии зафиксированы в `poetry.lock`. Изоляция обеспечивается Docker-контейнером - внутри него Poetry ставит всё из lock-файла, не опираясь на глобально установленные пакеты.

### 3. Конфигурация

Всё, что меняется между окружениями задаётся через переменные окружения: `DATABASE_URL`, `PORT`, `POSTGRES_USER` и т.д. Реальные значения лежат в `.env`, который исключён из Git через `.gitignore`. В репозитории есть `.env.example` как шаблон.

### 4. Сторонние ресурсы

PostgreSQL подключается через URL в переменной `DATABASE_URL`. Для смены БД (другой хост, облачный сервис) достаточно изменить переменную окружения.

### 5. Сборка, релиз, запись

- **Build:** `docker build` собирает образ, устанавливает зависимости из lock-файла
- **Release:** переменные из `.env` подставляются при запуске docker-compose
- **Run:** `docker-compose up` поднимает контейнеры

Стадии не смешиваются, код не собирается на лету.

### 6. Процессы

Бэкенд не хранит состояние в памяти между запросами. Все данные живут в PostgreSQL. Каждый запрос открывает соединение, выполняет операцию и возвращает результат. Процесс можно перезапустить в любой момент без потери данных.

### 7. Привязка портов

Uvicorn сам является HTTP-сервером и слушает порт из переменной `PORT` (по умолчанию 8000). Не требуется внешний веб-сервер. Порт пробрасывается наружу через docker-compose.

### 8. Параллелизм 

Uvicorn обрабатывает запросы асинхронно. Для большей нагрузки можно добавить воркеры или запустить несколько контейнеров за балансировщиком.

### 9. Утилизируемость

Uvicorn стартует за пару секунд и корректно завершается по SIGTERM . Контейнер можно убить и поднять заново,состояние в БД, а не в процессе. Данные не теряются при перезапуске.

### 10. Паритет разработки и продакшена

Docker Compose гарантирует одинаковый стек везде: та же версия Python, тот же PostgreSQL, те же зависимости из lock-файла. Разница между dev и prod - только значения переменных окружения, а не стек или сервисы.

### 11. Логирование

Приложение не пишет логи в файлы и не управляет их ротацией. Uvicorn сам выводит логи и ошибки в stdout/stderr. Сбор логов - ответственность среды исполнения (Docker, оркестратор). Логи не пропадают при пересоздании контейнера - их собирает внешний инструмент.

### 12. Административные задачи

Миграции БД вынесены в отдельный сервис `migrate` в docker-compose. Он работает в том же окружении, с тем же кодом и теми же зависимостями, что и основное приложение, но запускается как одноразовый процесс (`alembic upgrade head`). Бэкенд стартует только после его успешного завершения.
