## Доменная область

CarLog - приложение для учёта расходов на автомобиль. Пользователь регистрируется, заводит свои автомобили и ведёт по ним журнал: ТО, ремонты, заправки, страховки, мойки и прочее. Записи можно создавать, просматривать, редактировать, удалять, фильтровать по автомобилю, типу и периоду, а также смотреть по каждой машине статистику расходов.

## Стек реализации

| Компонент | Технология |
|---|---|
| Бэкенд (API) | Python 3.14, FastAPI, Uvicorn |
| Сервис авторизации | Python, FastAPI, PyJWT, PBKDF2-HMAC-SHA256 |
| Фронтенд | HTML + CSS + SA, раздаётся простым HTTP-сервером Python |
| Шлюз | nginx  |
| БД | PostgreSQL 16 |
| Доступ к БД | psycopg |
| Миграции | Alembic |
| Конфигурация | pydantic-settings |
| Зависимости | Poetry |
| Контейнеризация | Docker, Docker Compose |


- **gateway** - единственный сервис с пробросом порта наружу; маршрутизирует запросы.
- **frontend** - экран входа/регистрации, вкладки "Автомобили" и "Записи", фильтры, форма добавления/редактирования, окно статистики. Хранит JWT в `localStorage`, подставляет его в заголовок `Authorization`, обрабатывает ошибки API (в том числе 401 - возврат на экран входа).
- **auth-service** - регистрация и вход, выдача JWT.
- **backend** - бизнес-логика и CRUD по автомобилям и записям, проверка JWT.
- **migrate** - одноразовый контейнер `alembic upgrade head`.

## Основные сущности

- **User** - пользователь (`id`, `username` - уникален, `password_hash`).
- **Car** - автомобиль (`id`, `user_id` -> User, `brand`, `model`, `year`, `mileage`).
- **Record** - запись обслуживания (`id`, `car_id` -> Car, `date`, `kind`, `cost`, `note`).

Связи: User 1-N Car, Car 1-N Record; удаление каскадное (`ON DELETE CASCADE`).

### CRUD и бизнес-логика

CRUD (REST) реализован для `Car` (`/cars`) и `Record` (`/records`). Дополнительно:

- **Аутентификация и изоляция данных.** Каждый пользователь видит и изменяет только свои машины и записи; чужие объекты возвращают 404.
- **Правила предметной области:**
  - пробег автомобиля нельзя уменьшить (409);
  - дата записи не может быть в будущем и раньше года выпуска автомобиля (422);
  - тип записи - из справочника (`GET /kinds`);
  - запись можно привязать только к своей машине.
- **Статистика** `GET /cars/{id}/stats`: число записей, общая сумма, средние траты в месяц, последняя запись, разбивка по типам и по месяцам (агрегация в SQL).
- **Фильтрация записей**: `GET /records` с параметрами `car_id`, `kind`, `date_from` и `date_to`.
- **Валидация** входных данных (Pydantic) и обработка ошибок БД (409 при нарушении целостности, 503 при недоступности БД).

## Соответствие 12 факторам

### I. Кодовая база
Весь код лежит в одном репозитории. Один репозиторий - несколько развёртываний (разные `.env`). Бэкенд и auth-service собираются из одной кодовой базы одним образом и запускаются разными командами; общий код (`common/`) лежит там же.

### II. Зависимости
Зависимости явно объявлены в `pyproject.toml`, точные версии зафиксированы в `poetry.lock`. Установка выполняется внутри Docker-образа (`poetry install`) без опоры на системные пакеты, кроме `libpq5`, который ставится явно в Dockerfile. Фронтенд внешних зависимостей не имеет.

### III. Конфигурация
Всё, что отличается между окружениями, задаётся переменными окружения: `DATABASE_URL`, `JWT_SECRET`, `TOKEN_TTL_MIN`, `LOG_LEVEL`, порты сервисов, учётные данные PostgreSQL. Реальные значения лежат в `.env` (он в `.gitignore` и `.dockerignore`), в репозитории - шаблон `.env.example`. Секреты (`DATABASE_URL`, `JWT_SECRET`) в конфигурации приложения **не имеют значений по умолчанию**: если переменная не задана, сервис не запустится, а не подставит небезопасное значение.

### IV. Сторонние службы
PostgreSQL - подключаемый ресурс, адрес и учётные данные берутся из `DATABASE_URL`; чтобы сменить БД (другой хост, облачный PostgreSQL), достаточно поменять переменную, код не меняется. Сервисы `backend` и `auth-service` обращаются друг к другу не напрямую, а только через общую БД и общий токен. Сознательное упрощение: у двух сервисов **общая схема БД** (таблица `users` создаётся миграциями общего репозитория, на неё ссылается внешний ключ `cars.user_id`). Для учебного проекта это принято, в боевой системе у auth-сервиса была бы собственная БД.

### V. Сборка, релиз, выполнение
- **Сборка:** `docker compose build` - образ с зависимостями из lock-файла и кодом.
- **Релиз:** образ + конфигурация из `.env` (подстановка в `docker-compose.yml`) = релиз.
- **Выполнение:** `docker compose up` - запуск контейнеров; миграции выполняются до старта приложений.

### VI. Процессы
Cостояние живёт только в PostgreSQL, аутентификация - по самодостаточному JWT, сессий в памяти нет. Каждый запрос открывает соединение, выполняет операцию и закрывает его. Любой контейнер можно перезапустить или запустить в нескольких экземплярах без потери данных. На стороне клиента в `localStorage` хранится только токен и имя пользователя.

### VII. Привязка портов
Каждый сервис - самодостаточный HTTP-сервер, слушающий порт из переменной окружения (`BACKEND_PORT`, `AUTH_PORT`, `FRONTEND_PORT`, `GATEWAY_CONTAINER_PORT`). Внешнего веб-контейнера (Apache, Tomcat) не требуется. Наружу через `ports` публикуется только шлюз (`GATEWAY_PORT`); остальные сервисы доступны лишь внутри сети Compose.

### VIII. Параллелизм
Масштабирование - за счёт запуска дополнительных процессов (контейнеров), а не наращивания одного процесса. Так как сервисы stateless, `docker compose up --scale backend=N` работает без изменений кода; для балансировки достаточно настроить upstream в nginx. Внутри процесса Uvicorn обрабатывает запросы конкурентно, при необходимости можно задать число воркеров. 

### IX. Утилизируемость
Процессы быстро запускаются и корректно останавливаются: команды запуска используют `exec`, поэтому SIGTERM доставляется Uvicorn напрямую и тот завершается штатно. Соединения с БД не живут между запросами, а значит, не теряются при остановке. Состояние хранится в PostgreSQL (том `db_data`), поэтому контейнеры можно удалять и пересоздавать. Сервис `migrate` запускается один раз и завершается; приложения стартуют только после его успешного завершения (`service_completed_successfully`).

### X. Паритет разработки и production
Среда одинакова везде за счёт Docker: те же образы, та же версия Python, тот же PostgreSQL 16, те же зависимости из lock-файла. Различаются только значения переменных окружения. Миграции применяются тем же способом во всех окружениях.

### XI. Журналирование
Приложение не управляет файлами логов и их ротацией: все сервисы пишут события в stdout (`common/logging_setup.py`, единый формат с временем, уровнем и именем модуля), уровень задаётся переменной `LOG_LEVEL`. Логируются регистрация и вход, неудачные попытки входа, отклонённые токены, создание и удаление сущностей, нарушения бизнес-правил и недоступность БД. Сбор и хранение логов задача среды исполнения (`docker compose logs`, оркестратор или агрегатор логов). Пароли и токены в лог не попадают.

### XII. Задачи администрирования
Миграции БД выполняются отдельным одноразовым сервисом `migrate` (`alembic upgrade head`) из того же образа и с той же конфигурацией, что и приложение.
